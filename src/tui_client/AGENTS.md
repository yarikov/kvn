# Agent Guide: TUI client

This guide extends the root [`AGENTS.md`](../../AGENTS.md), whose rules apply here too. It covers `src/tui_client/`: the client loop, its message handlers, and the keys handled without the daemon. Read it before changing that code.

## Module Layout

- **`tui_client` submodules** (`src/tui_client/handler.rs` + `src/tui_client/handler/`, `src/tui_client/docs_preview.rs`): `handler.rs` owns `ClientLoop` (the loop's terminal/pane/log/toast/pointer state) and dispatches each `Msg`; the short branches (paste, snapshot, tick, resize, theme, reattach) stay there, while `mouse.rs` handles clicks, drags, wheel scrolling and log selection, `wheel.rs` the wheel step (one row per event, growing while events arrive in quick succession), `pointer.rs` the pointer shape plus double-click tracking, `scroll.rs` the queue of `ScrollViewport` requests (one in flight), and `toast.rs` the client-local toast stack: every `StateSnapshot::status_events` entry received since the client attached becomes a toast, newest first, and replaces the toast of its `StatusKey` in place (client-local toasts use `ToastKey::Editor` / `Scroll`). Each toast keeps its own deadline (3 s info, 7 s error); at most four are kept, and a new toast always shows: a full stack drops its oldest info toast, or its oldest error when it holds only errors, and `ui::widgets::ToastStack` draws them one row and one column in from the top-right corner, each as wide as its text, up to 40 columns, right edges aligned, leaving out what does not fit above the status bar. The client asks the daemon to clear an error only when it is the newest status (see [`src/app/AGENTS.md`](../app/AGENTS.md) § Status Events). `handler/key.rs` routes by `Model.overlay` to `key/{support,log_pane,clipboard,editor,quit,onboarding}.rs` — the client-local half of `app/update/key/`; `overlay` keeps `e` on Settings › Routing to open `routing.json` (`key/editor.rs`, `EditedFile::Routing`, at the selected row of the page, `Model::routing_settings_row`: the shown mode, one of its rules or its `final`) and `Enter` there (`key/routing_rules.rs`): with edited rules (`Model::routing_rules_edit`: the file as the page shows it, with each edited mode's `saved` rules as the base and its edited rules as the edit) it sends a correlated `ApplyEditedRouting` itself, and only once that is saved forwards `Enter` to apply the Mode row; a `Conflict` opens `$EDITOR` on the `YOUR EDIT` / `CURRENT` document (`EditedFile::RoutingRulesConflict`), and a failure is reported with the draft kept. `e` with edited rules opens that edit rather than the file on disk. It forwards every other overlay key. `docs_preview.rs` builds the fixed state used for documentation captures
- **Reattaching**: on `Msg::DaemonDisconnected` the loop reattaches, or exits with `TuiExit::Relaunch` to restart from the daemon's executable when the versions differ. Sends that fail with `DaemonConnectionLost` before that message arrives are ignored. Reattaching resets the toast's status revision to the new snapshot's, because a restarted daemon numbers statuses anew; `ClientLoop::report_error` keeps a client error it could not send and reports it after reattaching

## Terminal and External Tools

- **Input**: crossterm 0.29 can enable Kitty keyboard enhancements but drops the protocol's base-layout key code, so `input.rs` decodes terminal input itself: the physical `j` key stays `j` under a Cyrillic or Arabic layout.
- **Clipboard**: `wl-copy` reads stdin and then forks a background process that serves the selection. The client closes stdin before waiting, sends stdout and stderr to `/dev/null`, and calls `wait()` rather than `wait_with_output()`, which would wait for that background process to close the inherited pipes.
- **Editor**: `$VISUAL` / `$EDITOR` may carry flags (Omarchy 4 sets `EDITOR="omarchy-launch-editor --inline"`), so the value is split into a program and its arguments before `Command::new`.
