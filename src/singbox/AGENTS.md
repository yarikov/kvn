# Agent Guide: sing-box configuration

This guide extends the root [`AGENTS.md`](../../AGENTS.md), whose rules apply here too. It covers `src/singbox/` and the geo rule-sets it consumes (`src/geo.rs`): config generation, the Clash API port, routing modes, and the rule-sets they route. DNS generation is described with the DNS model in `src/config/AGENTS.md` § DNS Configuration. Read it before changing that code.

## sing-box Config Generation
- `singbox::config::generate_config` builds a complete sing-box 1.14+ JSON object from a `Profile` and `Settings`.
- The config is written atomically with mode `0600` to `$XDG_RUNTIME_DIR/kvn-tui/singbox.json`, validated with `sing-box check --disable-color` (its error reaches the status line and the app log without ANSI escapes), and only then is `sing-box run` spawned. The private `kvn-tui/` runtime directory has mode `0700`; a desktop user session with `XDG_RUNTIME_DIR` is required.
- The Clash API `external_controller` port is allocated per start by `net::allocate_loopback_port` and passed into `generate_config`; it is never a fixed number and never a user setting. `sing-box check` does **not** validate bindability (it exits 0 against an occupied controller port), so a conflict only appears when `sing-box run` fails. `runner::start` therefore retries up to `CLASH_API_START_ATTEMPTS` (3) times with a fresh port, but only when the failure names `address already in use` for that exact port — every other failure is returned immediately, and an exhausted retry keeps the original stderr in the error chain. The chosen port lives on `ProcessHandle`, so it cannot outlive the process; the daemon reads it from the process slot when executing `Effect::FetchTrafficStats`.
- If the process exits immediately, stderr is captured and surfaced to the user.
- sing-box's stdout goes to `/dev/null` and its stderr is piped; once the process survives the 300 ms readiness window, a drain thread forwards stderr to the `singbox` tracing target. An unread pipe fills at about 64 KiB and blocks sing-box on its next write.
- A REALITY profile without a uTLS fingerprint gets `chrome`, the default before schema v2; REALITY needs a fingerprint to work.
- The Clash API client reads only `GET /connections`, with every field `#[serde(default)]` because sing-box renames fields between versions, and a 2 s timeout so a stuck endpoint cannot pile up threads at the 1 Hz poll. sing-box resets its totals when it restarts, so a sample lower than the previous one yields a rate of 0.
- `build_outbound(profile)` dispatches to a per-protocol builder and returns `Vec<serde_json::Value>` (most protocols return one outbound; ShadowTLS returns two — a `shadowtls` wrapper tagged `shadowtls-wrap` plus a `shadowsocks` detour tagged `proxy`).
- `build_outbound` reads a stored `fm` on every protocol but Hysteria 2 (`apply_stream_finalmask` → `read_stream_finalmask`): a `fragment` TCP mask with `packets: "tlshello"` sets `tls.fragment` when the outbound has TLS over TCP — not on QUIC (TUIC, NaiveProxy over QUIC, a QUIC transport) and not on NaiveProxy, whose outbound refuses `fragment` (sing-box chooses split points and delays, so this approximates Xray's lengths and delays); other `fragment` settings, `quicParams`, and UDP masks on a TCP transport are inert and ignored; `header-custom` / `sudoku` / `xmc`, a UDP mask on TUIC, NaiveProxy over QUIC, a QUIC transport, or Shadowsocks / SOCKS5, which relay UDP straight to the server, and unknown keys fail generation naming them. `fm` itself is never rewritten here.
- Shared helpers: `build_tls_block` (TLS + ECH + REALITY; `disable_sni` keeps `server_name` for certificate verification and stops sending it in the ClientHello), `build_transport_block` (WebSocket / gRPC / HTTP / HTTPUpgrade / QUIC; each type emits only the fields sing-box accepts for it — the share link's host goes into `headers.Host` for WebSocket, and WebSocket early data into `max_early_data` / `early_data_header_name` and into a host list for HTTP; `Profile::share_link_params` is never emitted; an unknown kind is emitted as `{"type": kind}` so `sing-box check` names it, and QUIC with `quicSecurity` or `headerType` fails generation because sing-box would silently drop them; so does TCP HTTP header obfuscation (`http` with `headerType` in the profile's link params) when the outbound has TLS, because sing-box then speaks HTTP/2 instead of the HTTP/1.1 header Xray expects). VLESS (`security`) and VMess (`stream_security`) drop the `tls` block when the field is `none`; unset keeps it. `build_vless_outbound` likewise refuses VLESS Encryption (`encryption` other than `none`), which sing-box's VLESS outbound has no field for. `build_shadowsocks_outbound` passes the SIP002 `plugin` link parameter (`name;options`) as `plugin` / `plugin_opts`; sing-box ships `obfs-local` and `v2ray-plugin` and its check refuses any other name. `build_hysteria2_outbound` emits `obfs` as `salamander` or `gecko` (with `min_packet_size` / `max_packet_size` when set), and fails generation when an `obfs` link parameter is left in `share_link_params` — obfuscation the parser could not model must not be dropped silently. A stored `fm` must hold only client QUIC tuning, which sing-box has no field for and which does not affect the server: one `read_hysteria2_finalmask` rejects fails generation with that error, and one that still carries obfuscation or port hopping (an edited profile) fails with a re-import hint. `hop_interval` / `hop_interval_max` are emitted from `hop_interval_secs` / `hop_interval_max_secs` only next to `server_ports`. It turns the `mport` link parameter into `server_ports` (`a-b` → `a:b`, a single port `p` → `p:p`) and drops `server_port`, which conflicts with it. `build_outbound` refuses a `vcn` link parameter (Xray's `verifyPeerCertByName`, written by Remnawave and 3x-ui) that names anything but the SNI of a verified TLS block — the effective one, so the server address when `server_name` is empty, as sing-box does, compared case-insensitively and without a trailing dot: Xray accepts a certificate valid for any listed name, sing-box checks only `server_name`, and replacing `server_name` would change the SNI on the wire; `insecure`, REALITY and TLS-less outbounds verify no name, so `vcn` does not matter there. Hysteria's `pinSHA256` and S-UI's `pcs` (TUIC, AnyTLS) hash the whole certificate while sing-box's `certificate_public_key_sha256` hashes its public key, so the pin cannot be passed on; `config::certificate_pin_warning` makes `on_connected` show that it is not checked, next to `dns_bypass_warning`. `config::ech_dns_warning` warns there too when an ECH config is looked up in DNS (`ech_dns_lookup_names`) and the active preset's final server, which the direct lookup copies, is not DoH, DoT or DoQ. `build_naive_outbound` emits `username`, `password`, `quic` and the shared TLS block; sing-box 1.14 accepts only `server_name`, certificates and `ech` there and refuses `insecure` with a clear check error. A naive outbound carries no UDP (`proxy_carries_udp`). The embedded Chromium dials through sing-box's dialer and resolves through its DNS router; its UDP `connect()` to `2001:4860:4860::8888` is Chromium's IPv6 reachability probe (`HostResolverManager::StartGloballyReachableCheck`) and sends no data. No deprecated sing-box fields (no `obfs_password`, no `aes-128-cfb`, no top-level `dns.fakeip`, no WireGuard outbound).

## Routing Modes
- What a mode routes is data: `routing.json` `modes` (`config::routing::ModeDefinition { id, name, final, private_direct, rules: [{ rule_set, route, required }] }`, see `src/config/AGENTS.md` § Rule-Set File). The defaults (`config::routing::default_mode`) reproduce the old built-in modes: `global` — everything through the VPN; `bypass_<region>` — the region's rule-sets `direct`, `final: proxy`; `only_<region>` — the region's rule-sets `proxy`, `final: direct`; both with `private_direct` and every rule `required`.
- `RoutingMode` (`Global | Bypass(GeoRegion) | Only(GeoRegion)`, serialized as `global`, `bypass_<region>`, `only_<region>`; `RoutingMode::id`) is still the selection key until the region setting goes (plan stage C.3): it names a mode of `routing.json` by id.
- The available routing modes depend on the selected **geo region** (`Ru`, `Cn`, `Ir`, or `Global`): `RoutingMode::available(region)` lists the candidates and `GeoRouting::available_modes(routing)` keeps those `routing.json` declares (Global always).
- Geo-region and routing-mode preferences are grouped under `settings.geo_routing: GeoRouting`. It stores `current_region: Option<GeoRegion>` and `selected_region_modes: HashMap<GeoRegion, RoutingMode>`. The active mode (`GeoRouting::mode(routing)`) is derived from `selected_region_modes[current_region]` and falls back to `Global`, also when the stored mode is not one `available_modes` offers — including a mode removed from `routing.json` — (a hand-edited `bypass_cn` under `ru`), so the mode always names the current region. Switching back to a previously used region restores its last routing mode.
- **Rule-sets** are one entity, `geo::RuleSet { tag, kind, url }` (`Cow` strings), declared in `~/.config/kvn-tui/routing.json` (`config::routing::RoutingConfig`, see `src/config/AGENTS.md` § Rule-Set File). The `geo::RULE_SETS` catalog is only the defaults a new file is created with. `kind` is `RuleSetKind::Geosite` (domains) or `RuleSetKind::Geoip` (IP networks); it decides where the rule sits in the route (below) and whether a DNS rule naming the tag needs the `evaluate` / `match_response` pair, read from the routed plan entries (`RoutedRuleSets` in `build_config`). The tag is the sing-box rule-set tag, the name DNS preset rules refer to, and the local file is `<tag>.srs`. Modes name rule-sets by tag in their rules, and the plan resolves them in `RoutingConfig` (`RoutingConfig::rule_set`). `geo::region_rule_set_tags` lists a region's tags only for the default modes. A new region is a catalog entry plus a `region_rule_set_tags` arm; an existing `routing.json` keeps its own declarations.
- **Route plan** (`src/route_plan.rs`): `RoutePlan::for_mode` is the one place a routing mode turns into what it routes: it reads the mode's `routing.json` record (a mode missing there routes everything through the proxy) into ordered `PlanEntry { rule_set, outbound, required }`, whether private networks stay direct, the `final` outbound, and the fallback — everything to `final`: `RoutingFallback::Global` for `proxy`, `Direct` for `direct`. `GeoAvailability::lacks_rule_sets_of` and `routing_fallback` look only at `RoutePlan::required_rule_sets`, and `update/geo.rs::leave_routing_fallback` reconnects once those are present; a missing optional rule-set is just left out of the route. `build_route`, `DnsUpstreams` (whether DNS goes through the proxy) and `GeoAvailability::routing_fallback` read the plan, never `RoutingMode`. `route_plan::active_rule_sets(settings, routing)` lists the rule-sets of the active plan; it is the input for which files a start checks. Every function that builds a plan takes the `RoutingConfig` (`Model::routing`; `config::RoutingInput { settings, routing }` for `runner::start` and `generate_config`).
- Rule-sets are local `.srs` binary files downloaded to `~/.config/kvn-tui/geo/`. A file counts as present only when it starts with the `SRS` header and a version byte (`geo::rule_set_usable`, behind `RuleSetState::present` and the download decision in `GeoManager::refresh_rule_set`), so a damaged file is fetched again regardless of its ETag; `download_file` refuses to write a response without that header, so a captive portal never replaces a working file. `runner::collect_geo_availability` checks only the required rule-sets (one `GeoManager::states` call) and lists the usable ones by tag in `GeoAvailability::rule_sets`; `generate_config` reads paths only from there.
- `Bypass` / `Only` never run without the region's rule-sets. `generate_config` takes an `Option<RoutingFallback>`: with `None` it refuses such a mode (`GeoAvailability::lacks_rule_sets_of` the plan); `runner::start` asks `GeoAvailability::routing_fallback` instead and passes the mode's own default for all traffic — `Global` for `Bypass` (generated from `Settings::with_global_routing`) and `Direct` for `Only` (the `Only` config without region rules, `final: direct`; `Only` is used abroad with a server inside the region, so tunnelling everything would send all traffic into that country) — and reports it as `Msg::Connected { routing_fallback }`. `on_connected` checks the DNS and ECH warnings against the settings that actually run. `update/geo.rs` then downloads the plan's missing rule-sets (`fetch_region_rule_sets`; the path follows the running config — through the tunnel under Global, directly under Direct, past the kill switch either way through sing-box's marked traffic; a rule-set another download already fetches is left to it). Once no required rule-set is downloading, it reconnects when every one is present (`RuleSetState::present`, read from disk by the daemon), and otherwise keeps the fallback, with an error status naming the rule-sets that failed in that result, until a scheduled or manual geo update brings the files. `Model::routing_fallback` travels in `StateSnapshot` so the status bar shows `<mode> → Global` / `<mode> → Direct`.
- **Route order**: `build_route` emits one `rule_set → outbound` rule per plan entry whose file is present, placed by `kind`: `sniff` → `ip_is_private` → geosite rules → `resolve` → geoip rules.
  - A TUN connection carries only an IP, so domain rule-sets match only after `sniff`, which runs only while the destination has no name (`domain_regex: ["."]` + `invert`): sing-box matches a sniffed name ahead of the fake-IP name, so an SNI that differs from the queried name (ECH, domain fronting) would otherwise move the connection to another rule; with fake-IP the destination is a domain, so IP rule-sets match only after `resolve`, which queries the active preset's final server (tunnelled where DNS is) — never the direct `bootstrap` copy, and never the fake-IP server.
  - Each action is emitted only when a rule of its kind follows, so Global keeps the three base rules.
- **Rule-set sources and downloads**: the default rule-sets come from SagerNet (`sing-geoip` / `sing-geosite`). A download pass tries every rule-set even after one fails and keeps the ETags of those that succeeded, so one transient error does not force re-downloading its siblings. `METADATA_LOCK` serializes the read-modify-write of `metadata.json` across the detached download threads: atomic renames prevent corruption, not lost ETag updates.
- **Download state is kept per rule-set, keyed by `RuleSet::key()` (its file name)**; the region is never a key.
  - `metadata.json` holds `schedule_epoch` and one record per key: the `url` the file was downloaded from, ETag, `checked_at`, retry state and next update date. A record whose `url` differs from the rule-set's describes another source: reads treat the file as absent and the record as empty, and only a download adopts the new source (`GeoManager::adopt_source`, before each rule-set of `update_rule_sets`): it deletes the file, clears the record and records the new `url`, so a changed URL downloads at once instead of keeping the old file until its next update. The schedule writers and `record_outcome` leave a record of another source alone, so a client or a fallback with other URLs never deletes a file downloaded from the configured one; the TUI client does not touch `metadata.json` at all (`Model::from_config` takes the states from the snapshot). A record without `url` belongs to the current source. Loading an older file moves its `etags`, per-country ETag fields and per-region `checked_at` / `retry_states` / `region_next_update` onto the rule-sets of each region.
  - `GeoManager::update_rule_sets(list, only_missing, schedule)` returns one `RuleSetReport { key, tag, outcome }` per rule-set (`Updated`, `UpToDate`, `Failed`). Each rule-set's outcome is saved in one `metadata.json` write. A check that succeeds records `checked_at`; with a `ScheduleWrite` (an automatic update, or a missing-file download while auto-update is on) a failure records a retry and a success clears it and sets the next update date, both only while the schedule epoch still matches. `only_missing` skips a present file without a request.
  - `Effect::DownloadRuleSets { rule_sets, only_missing, record_schedule }` runs it and answers `Msg::RuleSetsUpdated { reports, states, epoch }`; `RefreshRuleSetStates` reloads `RuleSetState`s after a region change.
  - `Model::rule_set_updates: HashMap<key, UpdateTrigger>` lists the rule-sets downloading now, and `update/geo.rs::start_rule_set_download` skips any already in it, so one file never downloads twice at once and a result clears only its own keys. `geo_updating` in `StateSnapshot` is derived from it. `Model::rule_set_states` holds the per-key state; retry state and next update date from an older schedule epoch are ignored.
  - What is downloaded, refreshed on schedule and shown in the status bar's rule-set badge is `route_plan::selectable_rule_sets` — the rule-sets of every mode selectable in the current region, so switching between them needs no download. When the retry or next update date of any of them is due, the tick downloads every one not already downloading, so a region refreshes in one download and reconnects at most once; a rule-set it tried in the last minute (`Model::rule_set_automatic_attempts`) does not count as due, so a result that could not be saved does not restart the download on every tick. A downloaded rule-set reconnects the tunnel only when the running plan routes it.
