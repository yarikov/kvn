# Agent Guide: Daemon

This guide extends the root [`AGENTS.md`](../../AGENTS.md), whose rules apply here too. It covers `src/daemon/`: how effects are executed and where each kind of side effect lives. Read it before changing that code.

## Module Layout

- **`daemon` submodules** (`src/daemon/{effect,connection,geo,config_io,subscription,traffic,profile_test,process_slot}.rs`): Effect execution, mirroring the `app/update/` handler split: `effect.rs` is the `execute_daemon_effect` dispatcher only; `connection.rs` owns connect/disconnect, the polkit check and the tour's integration probe; `geo.rs` the rule-set download, state refresh and schedule reset; `config_io.rs` the revision-checked `profiles.json` commit, the support-prompt and onboarding-progress writes (including the failed-write recovery in `src/app/AGENTS.md` § First-Run Onboarding) and config reload; `subscription.rs`, `traffic.rs` and `profile_test.rs` one effect each (the last owns the temporary sing-box SOCKS5 latency probe); `process_slot.rs` the sing-box process slot, its poisoned-lock-safe accessors, the 250 ms ticker and exit polling

## Stopping sing-box

sing-box removes its `auto_route` / `strict_route` ip rules only when it exits on its own; after SIGKILL they stay, and IPv6 stays unreachable until the next start. `ProcessHandle::stop` therefore sends SIGTERM and waits `STOP_GRACE_PERIOD` (12 s: sing-box gives up closing by itself after 10 s) before SIGKILL. That wait never runs on the main loop: disconnect and reconnect move the handle into `ProcessSlot::retired`, and `stop_retired` stops it under `connect_coordinator` — on a disconnect thread, or at the start of the next connect thread, so a new sing-box never starts while the old one still holds the TUN interface. Daemon exit stops it synchronously.

## Retrying While sing-box Is Not Ready

pacman writes the new sing-box binary (a spawn while it is still open for writing fails with `ETXTBSY`) and installs it without file capabilities, which the ALPM hook sets only at the end of the transaction (sing-box then fails with `operation not permitted` on the TUN line). `runner::not_ready` tells these apart from every other start failure. `BinaryBeingWritten` comes from the context that `spawn_singbox` adds only to a spawn of sing-box itself. `TunNotPermitted` comes from a stderr line naming the TUN interface. `ENOENT` is not retried, because a missing binary is far more often not installed than mid-write. The daemon maps the reason to `ConnectRetryReason` for `Msg`, so the TEA core does not depend on `singbox::runner`. `connection::start_retrying_until_ready` then sends `Msg::ConnectRetrying` with the reason and its limit the first time it sees it, logs every not-ready failure to the journal, and restarts sing-box every `NOT_READY_RETRY_INTERVAL` (5 s), for up to `BINARY_WRITE_RETRY_LIMIT` (15 s) or `TUN_PERMISSION_RETRY_LIMIT` (2 min) from the first failure of that reason, under `connect_coordinator`, checking `is_current_attempt` between tries, so a disconnect, a newer connect or daemon shutdown (which advances the slot's attempt before taking the coordinator) ends it within `CANCEL_POLL_INTERVAL`. `RetryBudget` holds the per-reason limits and is unit-tested. The final failure keeps sing-box's stderr and adds a `kvn doctor` hint. Do not bring back a pacman lock or process check: an unprivileged daemon cannot tell a live lock from a stale one (#190).

## Config Saves

`config_io::persist_config_changes` commits `settings.json` and `profiles.json` after each `update`, before any effect runs, each on its own (`commit_file_change`: read the file's revision, three-way merge only that file's part with `merge::merge_file`, write with `write_if_unchanged`), settings first. An effect names its file; the update chooses how a failed write is undone:

- **`Effect::SaveProfiles` / `Effect::SaveSettings`** — a change the user asked for. A failed write restores that file's part of the config (and every file not yet committed) from before the update, together with the support prompt and tour progress, preserves the edited version under `recovery/` (`profiles.json.conflict-*` / `settings.json.conflict-*`), and drops every effect except `BroadcastState` and `AppendAppLog`: the change did not happen. A file committed before the failure stays committed.
- **`Effect::PersistConfirmedProfiles` / `Effect::PersistConfirmedSettings`** — a record of something the system already did (`Connected` writes `last_connected_profile` to `profiles.json`, `KillSwitchApplied` writes `kill_switch` to `settings.json`). A failed write keeps the model and every other effect, such as `WriteState`, and only reports the error: the model must describe the firewall and the tunnel as they are. The config the write was based on is kept in that file's `FilePersistence::unsaved_merge_base` and used as the merge base of every later save of the same file, so the unsaved state reads as the model's own change and wins over the older value on disk. A successful write of that file or a reload from disk clears it.
- A file that failed to load (`FilePersistence::blocked`) refuses every save of its own and of the editor; the other file saves as usual.

## Connect Attempts and the Latency Probe

- After every `update`, the run loop copies `Model::connect_attempt_id` into the process slot before any effect runs. `queue_connect` advances the ID one tick before `Effect::Connect`, so publishing it at once keeps a worker of the previous attempt from installing its process during those 250 ms.
- sing-box acknowledges a SOCKS5 `CONNECT` before the outbound connection is open, so the CONNECT round trip is about 0 ms. `profile_test` measures from the start of the HTTP request (or of the TLS handshake for HTTPS) to the first response byte through the tunnel.
