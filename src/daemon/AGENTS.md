# Agent Guide: Daemon

This guide extends the root [`AGENTS.md`](../../AGENTS.md), whose rules apply here too. It covers `src/daemon/`: how effects are executed and where each kind of side effect lives. Read it before changing that code.

## Module Layout

- **`daemon` submodules** (`src/daemon/{effect,connection,geo,config_io,subscription,traffic,profile_test,process_slot}.rs`): Effect execution, mirroring the `app/update/` handler split: `effect.rs` is the `execute_daemon_effect` dispatcher only; `connection.rs` owns connect/disconnect, the polkit check and the tour's integration probe; `geo.rs` the seven geo/service rule-set effects plus the shared refresh and result-finalizing helpers; `config_io.rs` the revision-checked `profiles.json` commit, the support-prompt and onboarding-progress writes (including the failed-write recovery in `src/app/AGENTS.md` § First-Run Onboarding) and config reload; `subscription.rs`, `traffic.rs` and `profile_test.rs` one effect each (the last owns the temporary sing-box SOCKS5 latency probe); `process_slot.rs` the sing-box process slot, its poisoned-lock-safe accessors, the 250 ms ticker and exit polling

## Stopping sing-box

sing-box removes its `auto_route` / `strict_route` ip rules only when it exits on its own; after SIGKILL they stay, and IPv6 stays unreachable until the next start. `ProcessHandle::stop` therefore sends SIGTERM and waits `STOP_GRACE_PERIOD` (12 s: sing-box gives up closing by itself after 10 s) before SIGKILL. That wait never runs on the main loop: disconnect and reconnect move the handle into `ProcessSlot::retired`, and `stop_retired` stops it under `connect_coordinator` — on a disconnect thread, or at the start of the next connect thread, so a new sing-box never starts while the old one still holds the TUN interface. Daemon exit stops it synchronously.

## Retrying While sing-box Is Not Ready

pacman writes the new sing-box binary (a spawn while it is still open for writing fails with `ETXTBSY`) and installs it without file capabilities, which the ALPM hook sets only at the end of the transaction (sing-box then fails with `operation not permitted` on the TUN line). `runner::not_ready` tells these apart from every other start failure. `BinaryBeingWritten` comes from the context that `spawn_singbox` adds only to a spawn of sing-box itself. `TunNotPermitted` comes from a stderr line naming the TUN interface. `ENOENT` is not retried, because a missing binary is far more often not installed than mid-write. The daemon maps the reason to `ConnectRetryReason` for `Msg`, so the TEA core does not depend on `singbox::runner`. `connection::start_retrying_until_ready` then sends `Msg::ConnectRetrying` with the reason and its limit the first time it sees it, logs every not-ready failure to the journal, and restarts sing-box every `NOT_READY_RETRY_INTERVAL` (5 s), for up to `BINARY_WRITE_RETRY_LIMIT` (15 s) or `TUN_PERMISSION_RETRY_LIMIT` (2 min) from the first failure of that reason, under `connect_coordinator`, checking `is_current_attempt` between tries, so a disconnect, a newer connect or daemon shutdown (which advances the slot's attempt before taking the coordinator) ends it within `CANCEL_POLL_INTERVAL`. `RetryBudget` holds the per-reason limits and is unit-tested. The final failure keeps sing-box's stderr and adds a `kvn doctor` hint. Do not bring back a pacman lock or process check: an unprivileged daemon cannot tell a live lock from a stale one (#190).

## Config Saves

`config_io::persist_config_changes` commits `profiles.json` after each `update`, before any effect runs. The update chooses how a failed write is undone:

- **`Effect::SaveConfig`** — a change the user asked for. A failed write restores the config, support prompt and tour progress from before the update, preserves the edited version under `recovery/`, and drops every effect except `BroadcastState` and `AppendAppLog`: the change did not happen.
- **`Effect::PersistConfirmedState`** — a record of something the system already did (`KillSwitchApplied`, `Connected`). A failed write keeps the model and every other effect, such as `WriteState`, and only reports the error: the model must describe the firewall and the tunnel as they are. The config the write was based on is kept in `Model::unsaved_state_merge_base` and used as the merge base of every later save, so the unsaved state reads as the model's own change and wins over the older value on disk. A successful write or a reload from disk clears it.
